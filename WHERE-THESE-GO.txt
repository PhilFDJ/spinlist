WHAT WAS ACTUALLY WRONG
-----------------------
The requests EVENT already expired at the end of the wedding day, which was
right. What was wrong was the button that opens requests: it was gated on
canEdit, which is the COUPLE'S EDIT LOCK.

So once the couple's lock date passed, "Make live requests" disappeared —
even though the requests themselves were meant to run on the night. Set a
lock two weeks out and the control for the gig was gone before the gig.

Now gated on its own rule: guest requests can be opened by the DJ side or
the couple right up to the end of the wedding day, and not after. The
couple's edit lock has nothing to do with it — that exists so you can
prepare a fixed set list a fortnight out, which is a different job.

A SECOND BUG, SAME LINE
-----------------------
canEdit is false for an ASSIGNED SUB-DJ entirely — they aren't the host and
aren't the couple. So a sub-DJ running the wedding could never open guest
requests, on the page or through the API.

Both now allow the host, the assigned sub-DJ, and the couple.

TURNING REQUESTS OFF
--------------------
Always allowed, including after the event — tidying up shouldn't be blocked
because the day has passed. Only turning them ON closes at end of day.
The page and the server agree on this; previously the page hid the toggle
after the event while the server would still have accepted it.

ENFORCED IN BOTH PLACES
-----------------------
The page hides the control and the API refuses with 423. A hidden button is
not a lock.

CHECKED ACROSS THE TIMELINE
---------------------------
  upcoming wedding, couple's lock already passed
    DJ / sub-DJ / couple  -> can open requests
  on the wedding day
    DJ / sub-DJ / couple  -> can open requests
  after the wedding
    nobody can open       -> but an already-live block can still be closed
